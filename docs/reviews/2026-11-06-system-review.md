# Enlumor 系统 review：这一系列东西为什么一直弄不好

日期：2026-11-06。依据的是提交 `42b2028`（`claude/roadmap-license-fix`，也就是 `feat/editing-default` 加上之后的文档），`.cache/acceptance/` 里的 34 份真实模型报告，以及 10-24 到 11-02 几次对话里你自己说的话。财务和商业模式不在这次范围内。

做法：8 个子 agent 各看一个维度（harness、模型接口、PDF 上下文、评测、AI 写入、产品交互、工程健康、开发流程），每个维度另派 1 个反方 agent，回到代码和报告里逐条核对。被驳倒的说法已经删掉，被改正的数字用的是核对后的值。下面的行号都是 `42b2028` 上的。

接下来怎么做，见[长期规划与施工计划](../plans/2026-11-06-agent-system-plan.md)。

## 一句话

卡住你的主要不是"harness engineering 太难、超出认知上限"，而是两件更基础的事没做：**没有一个大家都认的"当前代码"**，以及**改完以后没有便宜的办法知道改得好不好**。少了这两样，什么问题都没法排序、也没法宣布解决，自然就觉得每个问题都在挡路。agent 本身的核心代码只有约 210 行（`surfing-agent.ts` 88 行加 `surfing-requests.ts` 123 行），而且已经做成依赖注入，能离线测试。它是可以边做边学的大小。

## 先说做对了的，这些要保护好

1. **原文可核查的底线是结构性的，不是靠提示词。** 回答和带路步骤引用的段落 id 必须真实存在，否则不动阅读器（`surfing-agent.ts:44-45`、`surfing-route.ts:30`）。工具全部只读，论文文本明确标成不可信数据（`surfing-agent.ts:87`）。在同类 chat-PDF 工具里，这一点很少见。
2. **请求绑定文档版本。** 每次 await 之后都复查 documentId、指纹和版本（`surfing-requests.ts:59-103`），旧请求不会串到新文档。
3. **循环通过 ports 注入依赖**（`surfing-requests.ts:18-29`），`ai-client` 和 `surfing-*` 都不 import electron。不开窗口的离线评测和录制回放，接口已经现成。
4. **出错原因会回传给模型纠错一次**（`surfing-route.ts:7,30`）。164 次提问里用到纠错的 10 次，纠错后仍失败的只有 1 次。
5. **编辑库的地基很硬。** 文字标识必须先对源 PDF 逐字符核验几何（`editing-sources.ts:67-101`），事务、回执、可持久的撤销重做都有，升级前先做备份并逐表比对。将来 AI 不可能高亮一句论文里不存在的话。
6. **评测思路是对的。** 题目装在 PDF 的二维码里，合成论文 Lumen 专门对付"不看图也能答对"，还有一道考"论文里没有答案"的诚实题。缺的是版本绑定和重复测量，不是方向。
7. **密钥和网络边界收得紧。** 密钥用 safeStorage 加密，只允许 HTTPS，拒绝重定向，参数有白名单（`ai-config.ts:7-30`）。
8. **单元测试健康。** 本次实测 `npx tsc --noEmit` 约 2 秒通过，`npx vitest run` 44 个文件、683 个用例全绿，用时 19 秒。
9. **"带路"有真正的差异化。** 回答拆成有顺序的原文步骤，页面平滑滑过去。你说的"一直直接跳最后一步，你不知道前面的 process 是什么，那你还是没懂"，是对的教学直觉。

## 五个根因

### 根因 1：没有一个大家都认的"当前代码"

- `origin/main` 落后最新代码 40 个提交。PR #3、#4、#5 叠在一起，从 10-26 开到现在，评论和 review 都是 0。
- 本机有 7 个 worktree、27 个本地分支，最新的 5 个提交只存在这台电脑上。
- 新会话和新 worktree 默认从 `origin/main` 切出，可 main 早就不代表产品。"最新代码在 `feat/editing-default`"这句话只写在 Claude 的个人记忆里，仓库里没有，Codex、云端会话和新 worktree 都看不到。
- 已经出过至少 3 次事故，最近一次在 11-02：`open-source-monetization` 那个 worktree 在旧基线上重做了纠错回合和 JSON 解析，而最新分支 10-26 就有了（`fc59d75`）。两份实现的语义还互相冲突：旧基线版本对纯文字模型发出的 `view_page` 会耗掉唯一一次纠错，最新分支则要求回一句"看不到图"让模型继续答。

**为什么会这样**：为了基金定的代码冻结，顺带把"合并"也冻住了。基金结果出来以后，没有人回头做合并的决定；叠层 PR 又把合并变成"三件事一起拍板"，心理成本更高。

### 根因 2：改完以后，没有便宜的办法知道改得好不好

这是你说"无止境地砸 token，也不见得能解决"的直接来源。

- **结果不绑定代码和配置。** 34 份报告全部挤在 10-25 17:35 到 10-26 02:16（UTC）一个晚上，分布在大约 7 个代码状态上，冻结时的代码一次都没测过。`history.jsonl` 里没有提交号、提示词版本和思考档。
- **几乎每个配置只跑过 1 次**，没有留出集。同一难题集在 12 到 14 分之间波动，分不清是代码、思考档还是随机性造成的。
- **记录下来的失败，一多半是评测自己造成的。** 16 次失败里至少 9 次是：答案检测靠比较 DOM 文字、面板只留 6 条回答导致 180 秒超时、正则误判。11-02 的问题地图把其中 8 次超时归因到了"输出上限"上，这个归因是错的。
- **过程不落盘。** 模型每一步说了什么、工具返回了什么，都没有记录（只有 `console.warn`，`surfing-requests.ts:94-96`）。"它为什么没看图"查不出来。正在做的运行记录也按设计"never what was said"，还是同样的盲点，而且不绑定代码版本和思考档。
- **评测和 Electron 界面捆在一起。** 每改一次评分规则都得重新花钱调模型；跑一次要占着电脑和窗口焦点；两个 agent 同时跑 Electron 会互相抢焦点，把测量污染掉，中断的运行不留任何记录。
- **Surfing 的核心承诺没有被测。** 评分器只看答案里有没有关键词、有没有证据（`benchmark.ts:52` 只判断证据数大于 0），"引用的段落是否支撑这句话""带路带对了没有"完全没测。
- **头条成绩表**（6/6、8/8、13/14，思考与不思考的对比）是单次运行，两栏还来自不同的代码版本。

**为什么会这样**：评测是按"验收、演示能不能过"设计的，一次跑完、出一份好看的报告；它不是按"实验仪器"设计的。确定性的功能（阅读器、编辑库）用 RED→GREEN 一次就能证明改对了，概率性的 agent 不行，需要分数的分布和对照。流程没有为这个差别做调整。

钱其实不是瓶颈：按现有数据，一轮约 4 分钟；同一配置重复 5 次约 20 分钟，费用约 1 美元。瓶颈是看不清。

### 根因 3：harness 把应用自己能决定的事交给了模型

- **看不看图，完全由模型自己定。** 应用手里有图表索引（`surfing-figures.ts:7-16`），却只拿它塞进提示，从不用它驱动控制流。"Never describe a figure you have not viewed"没有任何代码强制（`surfing-agent.ts:17-18`）。关掉思考的三轮里，4 道必看图题 0 次看图，其中 2 道直接答错。默认档下也有约 1/6 的看图题没看图，还有两次用 `read_page` 代替了 `view_page`。
- **给模型的阅读和引用单位是 PDF 的"一行"。** Attention 被切成 662 段，中位长度 33 字符。组装后的提示约 1.97 万 token（o200k 口径，估算），纯文本只有约 8200，多了约 2.4 倍。摘要有 13 行，超过 8 条引用的上限，根本没法完整引用。114 个回答里有 32 个正好引用 8 条，这强烈说明上限被打满了，它是纠错的主要来源之一。原因是阅读器需要逐行的 quads 来高亮，于是高亮单位直接成了模型的阅读单位和引用单位。
- **全文常驻在每次请求里**，`read_page` 和 `search` 返回的是模型已经看过的同一批行，结构上就是冗余的。164 次提问里，看图用了 36 次，重读只有 5 次，搜索也只有 5 次。长论文没有任何降级路径。
- **AI 接口只能表达纯文字**（`src/shared/ai.ts:12-13`）：原生 tool calling、`tool_choice`、JSON 模式、显式缓存都接不进来。这一条在 DeepSeek 上的实际危害不大（纠错率约 6%），但"换任何模型都一样"在结构上做不到。
- **等回答时的正常阅读动作会直接取消请求。** 在 PDF 上滚一下滚轮、点一下、翻页、选字、点工具栏、切出窗口，都会触发 `notifyCruiseTakeover → interrupt → pause → cancelSurfing`（`main.tsx:98,401`，`index.ts:73`）。这是从 Cruise"读者接管就停下"沿用来的有意设计，还被测试锁住了。问题在于 Surfing 是"提问后等结果"，用户在 8 到 15 秒的等待里一定会去滚动、选字、回微信。验收脚本专门删掉了失焦监听（`real-model.spec.ts:118-119`），所以这个问题永远不会出现在分数里。
- **提示词、循环、解析、纠错、模式策略都挤在一个方法里**（`surfing-requests.ts:55-120`，第 71 行一行就有 2,095 字符），提示词没有版本号。你想做的每个 harness 实验都得改同一段密集代码。

**为什么会这样**：循环是边做边长出来的，没有把"策略"（看不看图、步数、何时纠错）和"机制"（发请求、计 token、取消）分开。

### 根因 4：产品上的关键决定，没有真实读者来裁决

- **带 Surfing 的版本从来没有发到任何读者手里。** GitHub 上没有安装包，正式版还是 0.1.15，阅读实验没做过。34 份报告只测了"模型答得对不对"。
- **Surfing 和 Cruise 的分工在代码里悄悄对调了。** v0.5.1 产品计划里，Surfing 是给"不知道从哪开始"的人用的、不用先提问；现在的 Surfing 是问答，"新 Cruise"又被定义成同一件事。这个关键转向是在一个 192 个文件的"sync"合并提交里进来的，git 历史里看不到决定和理由。
- **默认入口是"结论先行"**：先给一段完整解释，再自动带路，带路成了事后注解。这和"不替人思考"以及你自己要的"看到过程"有冲突。
- **"Enlumor 自己当 agent，还是给外部 agent 当工具""AI 要不要写 PDF"** 这两件事没定，harness 的规模就定不下来。如果先认定"帮新手读论文"是主任务，应用内的 harness 可以一直保持小而只读，那块"硬啃不下来"的东西会小很多。
- **新手上手要过好几道坎**：自带密钥、每次重新确认发送、没有获取密钥的指引、没有安装包。
- **题集反映的是你自己的阅读**（名论文的细节查找），不是目标读者会读的材料、会问的问题。

**为什么会这样**：一个人开发时，测量自然偏向一个人半夜就能跑的东西；需要别人参与的实验一直往后推，挑优先级时看的是"什么好测"而不是"什么最重要"。

### 根因 5：理解债，AI 的产出速度超过了一个人理解系统的速度

- **代码形态失控**：没有 formatter、没有 lint、没有 CI、没有文件大小上限。`main.tsx` 有 59.8 KB、428 行，`App` 一个组件里有 44 个 `useState`；`SurfingPanel.tsx` 平均每行 194 字节。Codex 从第一天就写成压缩风格，之后每次小改动都往长行里追加。结果是你没法审 diff，git blame 和断点失去意义，并行分支的冲突一行就有两千字符。
- **界面逻辑只能靠 e2e 测**，e2e 慢、抢焦点、会被失焦取消，机器负载高时随机变红，偶发失败已经被当成常态。
- **流程重在了错的地方**：已跟踪的 1,656 个文件里，`evidence/` 占了 1,400 个、约 31 MB（`src/` 只有 0.5 MB）；21 个回滚检查脚本从来没被调用过。与 harness 有关的设计文档却一份都没有。
- **编辑库为一个"通用 AI 编辑者"做得过重。** 规格追求"任何情况下都正确"，你批准了自己很难完整评估的规格，代码又压缩到读不了，也就没法反过来约束 agent。"超出认知上限"的感觉，有一部分是这样自己造出来的，并不全是 harness 本身难。
- **工作方式是"人定方向、agent 通宵产出、人早上验收"**，几家 AI 之间靠写给下一个 agent 看的文档交接。没有哪一步要求你能用自己的话讲清"这次 agent 循环改了什么、为什么"。
- **写给 agent 的"产品意图"文档已经过期，而且互相矛盾**，被推翻的 spec 也没有标作废。下次你说"把 AI 写入接上"，agent 很可能照着旧 spec 让 AI 直接写入，正好违背你对外的承诺。

### 五个根因怎么互相放大

没有公认的当前代码（1）→ agent 在旧代码上干活、重复干活 → 测量结果也对不上版本（2）→ 改了 harness 不知道有没有用（2、3）→ 只能再派 agent、再砸 token → 代码越写越密、文档越堆越多（5）→ 自己更看不懂，更依赖 agent → 产品决定被 agent 在会话里顺手做掉（4）→ 方向漂移，题集和读者脱节 → 测出来的数字更说明不了问题。

打破这个循环的口子在 1 和 2：先让 main 等于真实状态，再搭一个不开窗口、绑定版本、能重复、能回放的评测回路。之后每个问题都能变成每周可以看的数字。

## 现在就能修的具体 bug

这些不需要先做任何设计决定，修好就能少踩坑。

1. 等回答时滚动、点击、翻页、选字、切窗口会取消请求（H3）。
2. OpenAI 推理模型必然失败（M2）：按模型系列改发 `max_completion_tokens`，不发 `temperature`。
3. 星火走 Surfing 必然失败（M8）。
4. 同一个标识不能连续撤销（W7）。
5. 导出把所有标识写成用户的，移动过的便签导出后回到原位（W3）。
6. 带路结束后空格和方向键仍被劫持（P10）。
7. 三处发送范围说明互相矛盾（P5）。这涉及对外承诺，优先级比看起来高。
8. 提示里 `scope:'extracted-text-only'` 和能看图的矛盾，passage id 页码从 0 起（H12）。
9. 流式读取丢掉用量块（M4 的一部分）。
10. `npm run dev` 不构建 token worker（E9）。

## 对 11-02 问题地图的修正

[2026-11-02 的问题地图](2026-11-02-surfing-agent-problems.md)方向是对的，下面几处需要改：

- **"思考型模型超时已解决"不准确。** 早期 9 次 180 秒超时里，有 8 次是评测自己的问题（面板只留 6 条回答，答案检测靠比较 DOM），不是输出上限。
- **"每次请求约 1.2 万 token"偏低。** 按紧凑 JSON 和 o200k 估算约 2 万 token，主要是行级 passage 的 id 和 JSON 外壳造成的。
- **资源的去向要调整。** 先花钱跑 330 美元的评测矩阵是错的顺序：没有轨迹记录的矩阵，每多一个格子只是多一个解释不了的分数。应该先做轨迹记录、版本绑定和确定性看图，这些几乎不花钱；矩阵放到后面。
- **"该看图时不看"的第一步不是研究厂商的强制调用能力**，而是应用自己根据图表索引预取页面图，这件事现有接口就能做（`ai-client.ts:48` 的 turns 可以从 assistant 开始）。
- **头条成绩表是单次运行、跨代码版本**，对外讲的时候要说明。

## 需要你拍板的事

这些是产品决定，不是技术问题，会直接改变 harness 要做多大。规划文档里给出了建议和默认做法：

1. Surfing 的主任务：帮新手"开始读"，还是回答问题？
2. 等回答时用户翻页、选字：请求在后台继续（建议），还是保留暂停但支持重发？
3. 应用内的 agent 保持只读加"提议、确认"（建议），完整的"操作 PDF"留给外部 agent 通过 MCP 来做？
4. Surfing 是否先只承诺约 50 页以内的论文？
5. Cruise、星火、DashScope 原生协议：归档、隐藏还是继续维护？
6. 自己跑评测时，是否允许本机保存完整的模型原话，用来回放和诊断？
7. 三个叠着的 PR：直接快进合并到 main（建议），还是逐个合？
