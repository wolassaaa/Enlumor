> **Human-Centered Reading · 以人为本的 AI 原文共读**<br>
> **Product principle:** *Remove the friction, not the thinking.*<br>
> **Interaction principle:** *AI adapts to your thinking, not the other way around.*<br>
> **Status:** 已确认的产品与工程文档基线（2026-10-18）；本次仅整理文档，未修改应用代码<br>
> **Audience:** 项目作者、贡献者、Codex / Claude Code 等开发 Agent

## 0. 已确认方向与本次工程收敛

1. **Surfing 设为默认的 AI 共读入口**，而不是用户打开 PDF 后的强制启动流程。Reader 始终能独立使用。
2. **重新定义两个模式的职责**：Surfing 用于无预设问题的探索式阅读；Cruise 用于围绕用户问题的深入研究。可以分别进入，也能无缝切换。
3. **AI 负责引导，用户掌握节奏**：自动导航不等于自动夺取控制权。暂停、跳过、回看、调速、滚动和批注都必须即时响应。
4. **阅读速度与解释深度解耦**：推进快慢不应强制对应简略/详细的解释。
5. **产品优先验证 Surfing，工程优先复用现有阅读与 Cruise 底座**；先打通真实 API，再做最小可用 Surfing，不推翻已完成的工作。
6. **不引入 Surprisal 智慧热力图作为现阶段核心功能**。它衡量词语预测难度，不能直接视为用户阅读价值；将来可研究基于问题和原文证据的可关闭聚焦层。

**这一版的核心结论：先帮助人走进知识，再让人自由决定走多深。**

## 1. 问题定义与产品假设

### 1.1 观察到的用户困难

对尚未形成论文阅读习惯的学生而言，读论文经常是**必须完成，却很难开始**的任务：

- 不知道第一眼应该看哪部分，不理解论文常见结构。
- 专业术语、复杂句和背景知识造成高启动成本。
- 逐字阅读缓慢，思维想跳转或追问时，传统界面难以跟上。
- 在建立第一份有用理解之前，耐心已被搜索、切换、翻页和理解障碍消耗。

这些是**来自讨论和初步反馈的假设**，不是完成过正式实验的结论。不能假设所有读者都喜欢 AI 自动带读。

### 1.2 Enlumor 要解决的事

> 降低开始阅读和持续理解的阻力，让读者在原文中更快建立方向、找到证据，并在产生好奇心时自由深入。

**不以**最大化 AI 生成字数、阅读速度或自动翻页量作为产品目标。AI 讲完了，不等于用户读懂了。

### 1.3 北极星原则

1. **Human controls the pace.** 用户掌握阅读节奏。
2. **AI guides the exploration.** AI 引导探索，不替用户决定理解。
3. **Curiosity determines the depth.** 用户决定何时、向何处深入。
4. **The source remains central.** PDF 原文与可核验的证据始终是中心。
5. **Performance is a feature.** 阅读、滚动、缩放、批注不能被后台 AI 拖慢。

## 2. 模式定义：Reader / Surfing / Cruise

| 模式 | 用户当下的需求 | 系统职责 | 进度/方向控制 |
| --- | --- | --- | --- |
| **Reader**（自由阅读） | “我就想正常读 PDF。” | 提供完整、稳定、快速的阅读器 | 全部由用户控制，无 AI 依赖 |
| **Surfing**（探索阅读） | “我必须读，但不知道怎么开始，也不知道该看哪里。” | 在原文中自动寻找阅读路径、定位并简要讲解，按用户许可连续推进 | AI 建议路径；用户控制节奏和介入 |
| **Cruise**（深度研究） | “这个问题我想真正弄明白。” | 围绕用户目标检索、呈现可核验的原文证据，支持追问和批注 | 用户决定问题与每一步推进 |

**重要：** Surfing 不等于只能浅尝辄止；Cruise 不等于只能从 Surfing 进入。二者区别主要是**起点、导航方式、推进权**，而非固定的理解深浅。

### 2.1 初始入口

- 打开 PDF：默认进入 **Reader**，原文立即可读。
- AI 入口的首选行动：**Start Surfing / 开始探索**。
- 同级提供 **Ask a Question / 带着问题研究（Cruise）**，以及不启动 AI 的 Reader。
- 首次启动 Surfing **不强制**先读 Abstract、提交研究目标或完成复杂设置。
- 首次启动 Cruise：允许用户直接输入问题；可**建议**先读 Abstract / Introduction / TOC 形成问题，但不是阻断条件。

### 2.2 Surfing → Cruise（核心路径）

用户看到当前原文，产生“为什么作者选择这个方法？”等疑问时：

1. 点选 **Dive Deeper / 深入研究** 或直接提出问题。
2. **立即暂停 Surfing 的自动导航**，当前 PDF 页面与视图保持原位。
3. 将当前文档、选区/证据锚点、所在章节、已经呈现的内容和用户问题传入 Cruise。
4. Cruise 在已有上下文上检索和解释，不要求重新上传文件、重新读 Abstract，也不应无意义重复模型请求。
5. 可以从 Cruise 回到 Surfing：恢复到用户明确选择的位置；**不擅自重启自动推进**，必须有清晰的继续动作。

切换时必须防止旧请求在模式变更后操作页面。

## 3. Surfing 交互契约

### 3.1 控制权分配

| 项目 | 决策权 |
| --- | --- |
| 建议下一段/下一节/下一张图 | AI 提议；本地校验候选位置 |
| 显示哪段原文及对应解释 | 受当前路线、上下文与用户操作共同约束 |
| 速度（自动推进节奏） | **用户** |
| 解释深度（简洁 / 标准 / 详细） | **用户**，与速度独立 |
| 暂停、继续、跳过、回看、手动翻页 | **用户，立即响应** |
| 何时进入 Cruise、研究什么 | **用户** |
| 永久保存注释 | **用户明确确认** |

### 3.2 播放与介入语义

- `Play`：用户许可自动导航；每次真正推进前检查会话、模式、版本和用户最新的播放状态。
- `Pause`：立即停止后续自动导航。可以允许当前后台请求完成用于缓存，但**不得**因请求完成而偷偷移动视口。
- `Next/Skip`：立即进入下一有效原文块；旧请求结果不得覆盖新内容。
- `Previous`：回看之前呈现的原文块，不得伪造“已经读懂”的状态。
- 用户滚动、缩放、选择文字、点击跳转、批注或开始输入问题：**暂停自动导航**；不要强迫页面弹回 AI 指定位置。
- 切换标签页、文档或模式：取消或作废旧导航意图；恢复时依用户明确动作决定是否继续。
- 用户停留很久不等于已读；AI 已呈现不等于用户已读。

### 3.3 速度和深度必须独立

- **速度**：慢 / 正常 / 快，控制自动推进所提供的阅读时间、导航时机或用户定义的节奏策略。
- **解释深度**：简洁 / 标准 / 详细，控制解释粒度与展开内容。
- 不允许“快 = 必须输出短摘要”、“慢 = 必须输出长篇讲解”的硬绑定。
- 不根据文字长度或经过时间自动判断用户已理解。遇到尚未生成的下一块，应显示清晰的等待/可跳过状态，绝不冻结前台。
- 后续可研究自适应节奏，但必须可解释、可关闭，且不能覆盖用户显式设置。

### 3.4 AI 输出格式建议（协议，不限定模型厂商）

每个引导单元至少包含：

- `document_id`, `section_id`（如可用）, `anchor_ids[]`：对应可定位的原文证据。
- `role`：研究问题 / 背景 / 定义 / 方法 / 结果 / 限制 / 其他。
- `brief_explanation`：简洁、面向初学者的可读解释。
- `expanded_explanation`（可按需产生）：更深的细节。
- `why_this_next`：为什么引导阅读这一块（内部/可选展示）。
- `uncertainty` 或明确“原文不足以支持”的标记。

**严禁**仅凭 LLM 编造页码、坐标、证据位置或未出现在原文中的结论。候选锚点必须通过本地 PDF 文本层验证；无法定位时应显式降级，允许用户手动浏览。

## 4. Cruise 交互契约

Cruise 保持**问题驱动的半自动研究模式**，继续复用已有能力，而不是重新设计成 Surfing 的另一个播放器。

1. 用户可以自己提出研究问题；也可以从 Surfing 当前高亮/选区衍生问题。
2. 系统优先检索当前选区、相邻块及章节，再按需扩展到其他章节。
3. 展示原文证据和 AI 解释，并保留**一键返回原文位置**的能力。
4. 用户手动决定推进、追问、切换证据或保存批注。
5. 提醒读者区分作者实际声称、AI 归纳和尚待验证的推论。
6. 不把用户没有提出的问题强行塞入研究路径。

**目标隔离：** 同一文本块针对不同研究问题、解释深度、模型/服务配置产生的解释不得不加区分地复用。延迟返回的旧目标结果只能进入对应缓存，不得污染当前会话。

## 5. 技术架构：最薄共用底座

本次调整不要求推倒重写当前 Windows PDF 阅读器。优先复用现有 PDF 引擎、SQLite、文本定位、批注、会话和 AI Provider 适配层。

### 5.1 推荐模块边界

```text
PDF Renderer / Text Index / Annotation / SQLite
                    |
          Local Reader Commands
    search_text · get_block · show_evidence
    get_view_state · control_session
                    |
              Session Core
  document · mode · goal · cursor · request_version
  play_state · navigation_generation · reading_events
            /                   \
     Surfing Planner       Cruise Researcher
   (path + next block)     (question + evidence)
            \                   /
       Provider Adapter / Request Budget
                    |
                  LLM
```

这是**逻辑结构**，不要求按图新增一整套服务或目录。命令层保持轻量，优先调用现有本地函数；不要为实现“Agent 化”而消耗 token 或添加庞大插件系统。

### 5.2 状态与并发保护

至少区分以下概念：

- `document_id`：文档标识；避免跨文件结果混用。
- `session_id`：当前阅读会话。
- `mode`：Reader / Surfing / Cruise。
- `goal_version`：研究问题/任务变更递增。
- `navigation_generation`：用户主动控制视口、切换模式、跳转/暂停时递增或失效。
- `request_id` / `request_generation`：过期响应不准更新当前可见状态。
- `play_state`：是否允许 Surfing 继续自动导航。

**关键不变量：** 任何异步 AI 响应落地前，都需检查它是否仍属于当前可展示的会话与目标；所有自动视口移动都必须在执行前额外检查最新导航许可。旧结果可缓存，但不得抢占用户视口。

### 5.3 缓存和成本

**前置时机：**Wave B首次Surfing实现即建立文档/模式/任务版本/解释深度/Provider配置隔离；不沿用仅以block_id命中的缓存。Wave C在此基础上增加研究目标及goal_version，不把基本正确性拖到C。

- 解释缓存至少根据：文档版本、锚点/文本块、模式及任务/目标版本、解释深度、模型与 Provider 配置版本隔离；**绝不把 API Key 放入缓存键或日志**。
- Surfing 连续请求必须有**可持久化请求次数硬上限**，发送前原子预留额度；重试计数、并发竞争、重启恢复均需覆盖。
- 缓存命中不消耗模型请求额度；请求是否取消/失败、是否计费应分别记录。
- 向用户显示会向模型发送的文本范围；清楚区分 Provider 上报的 token/费用与本地估算。
- 不假设所有模型提供商都支持同一套原生 tool calling；结构化输出可以用兼容适配与本地校验实现。

### 5.4 性能硬约束

- 耗时PDF解析、批量文本分析和AI规划不得阻塞前台交互；复用PDF.js已有worker、异步I/O、有界分批与取消机制。异步网络等待本身不等于阻塞，不因此推倒重写现有阅读器。
- 滚动、缩放、批注、搜索和选区保持优先级；后台预取可被限流/中止。
- 针对长篇、多图、扫描件、公式、表格、复杂版面明确降级策略。
- 不能用“功能上可运行”替代实机帧时间、输入延迟、内存和长时间稳定性验证。
- 标准 PDF 批注导出必须继续可用；AI 提示高亮为**临时视觉层**，默认不写入永久 PDF 批注。

## 6. 交付路线：每 Wave 两项任务，测试后继续

> **优先级原则：产品验证 Surfing 优先；工程实现坚持现有 Cruise/PDF 基础先稳定。**<br>
> 若 v0.1.15 已有对应能力，应先审查、复用、补测试；不要机械重做。以下仅是规划，不代表功能已全部实现。

### 现有性能门禁（保留，不在本轮另选阈值）

以下为项目已在本机采用的回归预算，不是所有电脑和PDF的性能承诺：
- 200页文本/扫描样本，约32MiB与1000条批注；长图/公式/复杂版面另记录实际退化点。
- 解压后启动三次中位数≤1500ms；滚动帧时间p95≤34ms；阅读位置保存IPC p95≤20ms。
- 保留正文canvas≤30、缩略图canvas≤8；记录长任务、输入延迟、内存和长会话表现。
- 新增Surfing后在同样最终EXE与样本上对照Reader/后台AI运行结果；不得悄悄放宽原预算。
- 尚无已确认硬阈值的输入延迟/内存项目先建立并保存实测基线，不虚构通过数字。

### Wave A — 真实 AI 闭环 + 共用控制接口

**任务 A1：真实 API 验收**
- 优先使用用户选择的DeepSeek实际配置，在非Mock环境中验证PDF选块 → 请求 → 解释 → 原文锚点展示 → 当前证据块的追问。
- 追问只复用当前已验证证据块与必要的本轮问答上下文；不加入跨章节检索、完整研究路径或通用聊天平台。真实API模型ID以用户实际配置为准，不根据展示名称猜测。
- 测试模型错误、空返回、超时、限流、Provider 参数差异和重复提交。

**任务 A2：本地命令与用户优先控制**
- 整理并复用 `search_text`、`get_block`、`show_evidence`、`control_session` 等最小接口。
- 在 Cruise 中验证人工翻页/滚动、暂停、锚点跳转不会被旧响应覆盖。

**验收闸门：** 真实 API 完成可复现的端到端演示；异常可恢复；用户操作比 AI 结果拥有更高优先级。

### Wave B — Surfing MVP（重点）

**任务 B1：共用 Session + 安全自动推进**
- Reader / Surfing / Cruise 明确模式边界；建立 `play_state`、导航版本和旧请求拦截。
- 完成暂停、继续、跳过、回看、手动滚动自动暂停；设置持久化请求硬上限和发送范围提示。
- 同步落实基础缓存隔离、路线稳定位置和独立的已展示/已跳过事实；回看/重启依靠真实记录，不以AI完成代替用户确认。
- B只要求安全进入/退出Surfing并回到Reader；C再完善携带问题和证据的深度模式切换，避免B依赖尚未交付的C。

**任务 B2：无问题引导阅读**
- 无需Abstract或预设问题，即可从论文可解析内容建立有界、可展示的阅读路线；优先研究问题、方法、结果与限制等角色，不机械逐块播放标题、作者名单或参考文献。
- 某类证据未检测到或只扫描部分内容时明确说明；路线经过的范围不等于完整通读，不让模型补造缺失锚点。
- 自动定位原文 + 简洁讲解 + 用户许可下连续推进；至少可调整推进速度，解释深度独立。

**验收闸门：** 陌生论文可一键开始；连续阅读中用户随时接管；旧响应不抢视口；请求预算可靠；原文与引导说明可逐项核对。

### Wave C — Cruise 深度研究 + 模式切换

**任务 C1：目标驱动的 Cruise 完善**
- 支持用户从 Abstract / Introduction / TOC 建立问题，但不强制；优先原文证据检索。
- 在B已交付的基础缓存隔离上补齐研究目标与 `goal_version` 隔离；保留解释深度/Provider配置隔离，不重复建设或退回block_id单键缓存。

**任务 C2：Surfing ↔ Cruise 无缝切换**
- 继承文档、当前原文位置、选区、证据锚点和用户问题。
- 从 Surfing 进入 Cruise 时立即暂停自动导航；返回 Surfing 不自动恢复播放。

**验收闸门：** 同一篇真实论文连续切换多次，位置、问题、证据不丢失；不重复强制阅读 Abstract；切换前异步结果无法污染新模式。

### Wave D — 阅读可信度、恢复与性能验收

**任务 D1：阅读状态与可靠恢复**
- 在B已有基础记录上完善章节覆盖、历史与用户主动确认。是否呈现过、是否跳过、是否用户确认是独立事实，不是会互相覆盖的单一枚举；未访问由无相应事实推导。
- 用户确认已读不被之后的自动展示/跳过覆盖；AI已讲解单独记录，不以时间或AI展示自动推断理解。
- 重新打开文档/应用可恢复所选位置、模式及必要的历史状态；和永久批注数据分离。

**任务 D2：复杂 PDF / 压力测试 / 用户试读**
- 真实 API 长会话、长文档、复杂图表、并发 AI 请求下测试帧时间、内存、视口稳定性。
- 可延续“带专属二维码的基准测试 PDF”方案，作为**测试工具**而非普通阅读功能。
- 邀请真实新手进行 Surfing 与 Reader/Cruise 对比试读。

**验收闸门：** 性能不因后台 AI 明显退化；阅读记录无伪造；异常和重启可恢复；有真实用户测试记录。

## 7. 初期用户测试设计

**目的：** 验证 Surfing 是否降低阅读启动困难，而不是证明用户一定喜欢自动模式。

建议招募 5–10 名不同论文阅读经验的学生，先进行小规模定性试读，再考虑更严格的对照测试。记录用户原话、操作行为和出现疑惑的节点。

**问题与证据：**

1. **开始是否容易？** 无指导情况下，用户能否顺利开始看原文？
2. **首次有用理解有多快？** 用户什么时候第一次能够自己说出论文研究问题或方法？（*Time to First Insight*，需用户表达或简要核实，不能由模型独断。）
3. **是否真的理解？** 看完后能否复述核心方法、一个结论以及至少一项限制，而不是复读 AI 讲解。
4. **节奏是否被尊重？** 记录暂停、跳过、回看、手动接管、AI 干扰视口的频率和场景。
5. **是否自然产生问题？** 有没有从 Surfing 主动进入 Cruise，为什么？
6. **是否愿意再用？** 第二篇类似任务是否愿意自愿选择 Enlumor；原因是什么？

**不要诱导性提问**“你是不是更喜欢 Surfing？”可先问“平常卡在哪里、你会怎么处理”，再展示两种模式。兴趣表达不是留存或学习效果的证明。

## 8. 本期明确不做（Non-goals）

- 不做基于 Surprisal 的逐词智慧热力图作为 MVP 关键功能。
- 不为了 AI 自动化而隐藏原文、强制读摘要或默认跳过所有复杂证据。
- 不添加大型多 Agent、向量数据库、云同步平台或独立插件生态作为前置条件。
- 不默认将 AI 建议的高亮、下划线和笔记写成永久 PDF 注释。
- 不自动判定用户“读完了”“理解了”，也不凭停留时间计入阅读完成度。
- 不把商业化、订阅或作者替所有用户承担模型调用费用设为项目目标。

**保持：开源、Local-first、BYOK（Bring Your Own Key），优先解决作者和真实读者的阅读问题。**

## 9. 给开发 Agent 的执行约束

将本文作为**产品意图与验收标准**，不要在不了解仓库现状的情况下直接据此大规模改写。

实施某个 Wave 前：

1. **先审计现状**：列出已实现、部分实现、未实现；说明与本 MD 的差距。
2. **只拆当前两项任务**：给出拟修改文件、数据结构/状态变化、风险与最小测试计划。
3. **先最小闭环，后优化**：以可验证真实路径为准，不以 Mock 通过代表真实 API 可用。
4. **每完成一个 Wave 停下来验收**，不要自动扩展到后续功能。
5. **一旦新设计与性能、原文可核验性、用户控制权冲突，以本文件第 1.3 节原则优先**；明确报告取舍。
6. **不要虚构已实现功能或测试数据**；实际状态由仓库代码和测试报告决定。

### Definition of Done（适用于所有 Wave）

- [ ] 核心交互在真实 PDF 上可手动复现。
- [ ] 失败、取消、超时、重试、模式切换路径有测试。
- [ ] 没有旧 AI 响应抢占用户操作。
- [ ] 前台 PDF 阅读/滚动/缩放/批注无明显退化。
- [ ] 模型输出能关联到原文证据或明确声明无法定位。
- [ ] 本 Wave 的新接口、数据迁移及用户可见行为有文档记录。

**Enlumor 是一款以 PDF 原文为中心、由用户掌握阅读节奏的 AI 共读工具：先用 Surfing 帮人开始并探索，再用 Cruise 跟随人的好奇心深入研究。**
