# Enlumor 长期愿景与分阶段计划

这份文档写的是 Enlumor 更远的方向：它从哪里来，可能走到哪里，每一步在什么条件下才开始做。它不是开发任务，也没有排期。近期要做的事见[路线图](ROADMAP.md)，现状见[当前开发状态](CURRENT_DEVELOPMENT.md)。

核心目标不变：**Remove the friction, not the thinking.** 消除阅读和研究里的阻力，不替人思考。

## 这个方向是怎么来的

1. **论文难读。** 很多本科生没有系统读过论文，面对陌生术语和长篇论证，不知道从哪里开始，逐字读又很快耗尽耐心。
2. **AI 总结不够。** 总结省时间，但会丢掉前因后果，有时和原文不符，也跳过了读者自己提炼、组织论证的过程。我们不拒绝 AI，只是不希望它的输出代替阅读和思考。
3. **所以 AI 应该辅助读原文。** 这就是 Reader、Surfing、Cruise 三种模式的出发点。
4. **读的时候会产生问题，问题会变成研究，研究会积累证据。**
5. **证据应该能直接进入写作。** 这一步来自学术写作课上学的 Claim / Grounds / Warrant / Counterargument：既然 Enlumor 能帮人在原文里找到证据，这些证据和读者当时写下的理解，就应该能成为后来写文章时论证的材料，而不是每换一个软件就从头再找。
6. **人和 AI 需要一个连续的知识工作环境。** 现在阅读、文献管理、笔记、写作、AI 对话分散在不同工具里，上下文要反复重建。

这是一条可能的发展路径，还没有被证明正确。Enlumor 最终可能成为完整的学术工作空间，也可能一直是一款好用的 AI 阅读器，两种结果都可以接受。

## 长期原则

- **原文优先**：原文始终在场。AI 的解释尽量对应到能核查的原文位置，并分清哪些是作者说的、哪些是 AI 的归纳、哪些是读者自己的观点。
- **人保有控制权**：节奏、方向、选区、批注、是否采纳 AI 的建议、何时结束，都由人决定。"给读者看过"不等于"读者读过、读懂了"。
- **性能本身就是功能**：AI 不能让滚动、缩放、批注变慢，也不能抢走当前视口。
- **不绑定模型，自带密钥**：可以换不同的模型服务；密钥和花费由用户掌控。Enlumor 只做工具，用哪家模型、怎么付费由用户自己决定。
- **本地优先**：文件、批注、笔记、阅读和写作记录默认留在本地。发给云端模型的范围要明确，用户可以控制。
- **过程记录归用户所有**：将来如果能导出阅读和写作过程，用来证明自己真的读过、理解过，也必须由用户决定是否分享，绝不默认上传或替任何人监控。
- **开源**：方便检查、修改和长期维护。开源本身不是竞争优势，优势要靠体验和可核查性来建立。

## 分阶段计划

每个阶段都有"进入条件"。条件没满足，就不开始做下一阶段，新想法先记进 [BACKLOG](BACKLOG.md)。

### 第一阶段：阅读（当前）

**目标**：Reader、Surfing、Cruise 成为一个自己和别人愿意长期使用的阅读工具。

**已经有的**：完整的阅读和批注；编辑库可以区分修改来自用户还是 AI；Surfing 针对全文问答，并一步步带读者看原文；真实模型验收工具。

**还要做的**（详见[路线图](ROADMAP.md)）：

- **决定 Surfing 的定位。** 原计划里，Surfing 是给"不知道从哪开始读"的人用的，由 AI 规划阅读路径；现在的实现需要读者先提一个问题。要么加一个不用提问的入口（比如"带我读这篇论文"），要么重新划分 Surfing 和 Cruise 的边界。这是冻结之后第一个要做的产品决定。
- 重做 Cruise，围绕读者自己的研究问题。
- 多模型评测：换模型、换思考档位以后，是否还可靠，便宜的模型够不够用。
- 小规模阅读实验：同一篇论文、同一个问题，比较不用 AI、直接给答案、一步步带读三种情况。
- 解决大量笔画时的卡顿，以及几项偶发失败的测试。

**进入下一阶段的条件**：阅读实验有了初步结果；有人在演示之外真的反复使用；Reader 的性能达到预算。

### 第二阶段：证据

**目标**：读者在阅读中标记的证据，连同自己写下的理解，成为可以再找到、再引用的东西。

**最小做法**：

- 一条证据 = 原文位置（文档身份、页码、锚点）+ 引文 + 读者自己的理解。读者的理解和 AI 的解释分开存放，不能互相冒充。
- AI 可以提议标注，读者确认后才写入，并标明来源，可以撤销。
- 在自己所有的批注和证据里跨文档检索。
- 导出带出处的引文（先支持常用格式，比如 APA，再支持 BibTeX）。
- 提供回到原文的链接（例如 `enlumor://`）：在别的软件里点一下，就能回到 Enlumor 里的原文位置。
- 和 Zotero 互通：读取 Zotero 的文献条目和引用键。Enlumor 只负责证据这一层，不做文献管理器。

**进入下一阶段的条件**：用户确实在多篇论文里积累了证据，并且有人主动想在写作时用它们。

### 第三阶段：论证与写作

**目标**：从证据自然过渡到组织论证。重点是论证结构，不是写作格式。

**最小做法**：

- 一个论证提纲：每个 Claim 下面挂着支持它的证据（Grounds）、为什么能支持（Warrant），以及反方观点（Counterargument）。每条证据都能点回原文核对。
- AI 的角色是检查：哪个 Claim 缺证据，哪条证据其实不支持这个论点，哪里的推理有跳跃。它不生成整篇文章，也不能编造引用、数据或作者的意思。
- 导出：先导出为 Word 和 Markdown 能直接用的提纲和引文，因为本科生的论文大多用 Word 写；LaTeX/BibTeX 作为面向研究生的选项。
- 不做编辑器，不重造 TeX，也不复制 Overleaf。

**进入下一阶段的条件**：有真实的写作任务在用这条链路，而不只是演示。

### 第四阶段：学术工作空间（只做探索）

跨任务的 AI 助手、协作研究、插件接口、多文献分析等，现在只是可能性，不是承诺。真到这一步时，根据前三个阶段的实际使用情况再决定。

## 接入方式：Enlumor 只做工具

Enlumor 不卖模型额度，也不替用户决定用哪家服务。谁用谁接，接法有三种：

- **自己填 API**：DeepSeek、OpenAI、Claude 等，或者任何 OpenAI 兼容的地址。用户填什么就用什么，文档里不点名推荐、不内置第三方中转服务，因为它们能看到发出去的原文和密钥。
- **本地模型**：例如用 Ollama 运行开源模型，数据不离开电脑。
- **把 Enlumor 做成 MCP 服务器**：把看页面、读原文、搜索、跳转、高亮、读取证据这些能力，作为标准工具开放出去。用户用自己的 Claude Code、Codex、Antigravity 或其他 Agent 连进来，用 Enlumor 读自己的论文和证据。模型和订阅都是用户自己的，Enlumor 只负责原文、证据和界面。

MCP 这条路和现在的设计是一致的：Surfing 本来就是模型调用翻页、读原文、搜索这些工具，再把结果呈现给读者，做 MCP 就是把同一套工具开放出去。它适合在第二阶段（证据）之后考虑：那时 Enlumor 里不只有一篇 PDF，还有读者积累的证据和理解，外部 Agent 能用的东西才足够多。开放出去的工具同样要遵守上面的原则：写入要读者确认并标明来源，发出去的范围由用户控制。

## 现在就要守住的事

为了不把将来的路堵死，今天不需要新增任何架构，只要守住已经有的东西：

1. **证据身份稳定**：文档身份、指纹、页码和锚点，不能被以后的改动弄乱。
2. **用户内容和 AI 内容分开**：编辑库现在能区分修改来自谁，以后 AI 有了写入入口，也要继续保持。
3. **打开 PDF 默认进入 Reader**：不自动发起模型请求；发送全文要先确认。
4. **不修改原文件**：导出时另存一份。

## 现在明确不做的事

文献库、LaTeX 编辑器、论证图界面、插件系统、多人协作、通用的 AI Agent 框架、为未来功能提前搭的多层平台。这些等前面阶段的条件满足了再说。

## 公开之前已经定下来的事

- **开源许可证**：已选定 AGPL-3.0-or-later，继续使用 PyMuPDF，不更换 PDF 引擎。

## 怎么判断方向对不对

- 用户能不能更容易地开始读一篇陌生论文？
- 能不能在合理的时间里得到正确、能复述、能追溯到原文的理解？
- AI 是在帮人形成自己的判断，还是让人只会看 AI 的输出？
- 写作时能不能很快找到一条论据背后的原文？
- 加了新功能以后，阅读和批注是否依然流畅？
- 用户是否真的在反复使用，而不只是觉得演示很酷？

目前的依据只有个人体验、一位外部大学生的公开讨论，和少数同学的反馈，都还不是验证过的结论。
