## 一、先说结论

1. **卡住你的主要不是 harness 太难。**
   - agent 的核心集中在两个文件里，合计约 2.3 万字节，而且已经做成依赖注入。现在看起来只有约 210 行，是因为很多代码挤在一行里，格式化后估计五六百行。
   - 真正缺的是两样东西：一个大家都认的"当前代码"，以及一个便宜、能重复、绑定版本的"改动→测量→决定"回路。
   - 前 7 周以这两件事为主，只顺手修几个读者马上会碰到的小问题。
2. **应用自己能决定的事，不交给模型。**
   - 看不看图、引用几条、什么时候停，由代码来定；模型只负责理解和表达。
   - "强制看图"没法靠厂商的 `tool_choice` 实现。调研确认，DeepSeek 和 Qwen 在思考模式下一强制就报 400，最新的 Claude 一律拒绝强制调用。
   - 所以只能由应用预取页面图，再加一道代码校验门。
3. **Enlumor 应用内的 agent 保持"小而只读，写入只做提议"。**
   - 完整的"操作我的 PDF"留给用户自己的 agent（Claude Code、Codex 等），通过 MCP 来做。
   - 这样你那块"硬啃不下来"的东西会小很多，也和"Enlumor 只做工具"的原则一致。
4. **先证明对读者有用，再扩功能。**
   - 学习研究的结论相当一致：直接给答案或摘要会让人"觉得懂了"，实际理解不变，甚至下降；带来收益的是要求读者先动脑的引导。
   - 所以默认入口要从"结论先行加自动带路"改成"读者发起、读者控速"。
   - 第 6 周就请 1 到 2 位同学试用现有版本，不等新功能。
5. **不换整套 agent 框架，也不再全部手写。**
   - Surfing 的小循环自己掌控。
   - 只把"各家模型接口"这一层换成成熟的库（Vercel AI SDK 的 provider 包，Apache-2.0）。参数名、用量读取、能力判断这类 bug 恰好都出在这一层。

## 二、几个会反复出现的词

| 词 | 意思 |
| --- | --- |
| harness | 模型外面那一圈程序：给模型准备材料，接收回答，检查，决定下一步。Surfing 的 harness 主要是 `surfing-requests.ts` 和 `surfing-agent.ts`。 |
| trace（运行轨迹） | 一次回答从头到尾每一步的记录，相当于飞机的黑匣子。 |
| 回放（replay） | 把一次真实的模型回复录下来。以后改代码时用录音代替真实模型，不花钱，结果也固定。 |
| 段落单位（passage） | 发给模型、也让模型引用的最小文字块。现在是一行，计划改成一段。 |
| quads | 高亮一行字用的四个角的坐标。 |
| parserVersion | 抽取程序的版本号。抽取方式一变，旧编号可能对不上，带着版本号才知道要不要重新对齐。 |
| 锚点 | 在 PDF 里重新找到一段文字的办法。只记"第几页第几段"，抽取一变就会找错；记下引文和前后几十个字，就找得回来。W3C Web Annotation 和 Hypothesis 用的是后一种。 |
| JSON-in-prompt | 在提示词里要求模型按 JSON 格式回答，由应用自己解析。与之相对的是厂商的"原生工具调用"接口。 |
| reducer | 一个只管"现在是什么状态、收到什么事件、下一步做什么"的函数。它不碰界面和网络，所以能直接写单元测试。 |
| ModelPort | 应用和各家模型之间的统一接口，换厂商只换这一层。 |
| 冒烟测试 | 发几个极短的请求，看最基本的功能通不通，像电器通电后先看有没有冒烟。 |
| pass^3 | 同一道题跑 3 次都对才算对，用来看稳不稳定。 |
| MCP、stdio | MCP 是一种标准接口，让 Claude Code、Codex 这类外部 agent 调用别的程序提供的工具。stdio 是它最简单的连接方式：外部 agent 在本机启动一个小程序，通过标准输入输出交流，不开网络端口。 |
| BYOK | 用户自带密钥（Bring Your Own Key）。 |

## 四、目标形态：agent 系统长什么样

### 4.1 先定位置：谁是 agent

| 场景 | 谁来当 harness | Enlumor 负责什么 |
| --- | --- | --- |
| 新手读一篇论文（主场景） | Enlumor 自己的小循环 | 全部：原文、工具、引导、界面 |
| 高级用户让 agent"操作我的 PDF"、跨论文整理 | 用户自己的 agent（Claude Code、Codex 等） | 通过 MCP 提供只读工具和"提交建议"，写入仍由读者在 Enlumor 里确认 |

所以应用内的循环可以一直很小：最多几步，只读，写入只产生"建议"。复杂的多步规划不放进应用，以后需要时交给外部 agent。

### 4.2 分层，以及每层什么时候建

从下往上：

1. **文档层（DocumentModel）**
   - 一篇 PDF 只抽取一次，所有功能共用。
   - 单位是段落（可以细到句子）。每段带逐行 quads、章节路径、所在页、图表关联，以及由文档指纹、parserVersion、引文和前后文组成的稳定锚点。
   - 现在有三条抽取管线：Cruise、Surfing、编辑库。
   - 什么时候建：段落单位在第 9 到 10 周。文本清理和稳定锚点在第二季度，必须在任何 AI 写入之前完成。编辑库那条管线在做锚点时一起并入。
2. **工具层（ToolRegistry）**
   - 每个工具有名字、写给"新同事"看的说明、参数 schema、风险级别（只读、提议、写入）和预算消耗。
   - 应用内的 Surfing 和将来的 MCP 服务器共用同一份注册表。
   - 什么时候建：第 8 周把现有的 3 个工具搬进注册表；风险级别等做写入时再用上。
3. **策略层（Policy）**
   - 应用能自己决定的事都放在这里：图表题预取页面图；回答被接受前的代码校验门；整题的 token、时间和请求数预算；重试；取消规则（只有"停止"、新问题、关闭文档才取消）；AI 身份的写入一律降级为"建议"。
   - 什么时候建：第 8 周先放预算、重试和取消规则，第 12 周加看图策略。
4. **循环（reducer）**
   - 形式是 `(状态, 事件) → (新状态, 下一步动作)`。它是纯函数，不依赖 Electron 和 React，在 vitest 里就能直接驱动。
   - 提示词放在单独的文件里，带版本哈希。
   - 什么时候建：第 8 周。
5. **模型端口（ModelPort）**
   - 统一的流式事件：文本、思考、工具调用、用量、结束。下面接 Vercel AI SDK 的各家 provider 包。
   - 原生工具调用只在用真实 key 验证过的厂商上打开，其余继续走 JSON-in-prompt。
   - 能力不再按模型名猜，改成三层：随版本打包的能力快照；用户在设置页点"验证"时发的冒烟测试；用户手动覆盖。
   - 换库时，现有的网络边界要原样保住：只走 HTTPS、拒绝重定向、参数走白名单。
   - 什么时候建：第二季度。
6. **黑匣子（trace）**
   - 每次运行写一份本机 JSONL，字段名沿用 OpenTelemetry GenAI 的命名。
   - 默认只记结构和数字，不记原文；绝不记 API Key。具体字段见第 1 阶段第 3 条。
   - 什么时候建：第 4 周。
7. **评测（eval）**
   - 包括：不开 Electron 的 Node runner、录制回放、抽取回归集、分层评分器、决策规则。
   - 什么时候建：第 5 到 7 周。
8. **界面**
   - 读者发起的带路在第二季度做；安静伴读做不做、做成什么样，等第 3 阶段的研究结果再定；建议托盘在第 5 阶段做。
   - 界面只订阅状态，不持有请求。

除了黑匣子、评测和模型端口是新加的，其余各层大多是把现有代码拆开、各归其位，不是另建一个平台。用不到的层不提前搭，这和 VISION"今天不需要新增任何架构"的意思一致。

### 4.3 四条设计规则

- **一次只改一个组件，然后测量。** 不要在同一个 PR 里同时换模型接口、改提示词、改引用单位，否则评测结果没法归因。
- **每条测量都绑定版本。** 没有提交号、配置和题集指纹的数字，不写进文档。
- **对外承诺只有一个来源。** "发给模型的是什么""发给 MCP 客户端的是什么"由代码生成一份说明。README、确认框和设置页都从这里取。
- **花用户的钱要看得见。** 额外的请求要么由用户点按钮触发，要么计入整题预算，并在界面上显示出来。

### 第 1 阶段：黑匣子和测量仪器（第 3 到 7 周）

**目标**：从此以后，任何 harness 改动都能用一个可信的数字回答"有没有用"，而且大部分迭代不花钱。

1. **一次性格式化（第 3 周）。**
   - 前提：PR 都已经合进 main。顺序很重要，必须先合并再格式化。
   - 单独开一个只有格式变化的 PR，用 Prettier（行宽 100）格式化全仓，用 merge commit 合并。
   - 把这个提交写进 `.git-blame-ignore-revs`，这样 `git blame` 会跳过它。
   - lint 用 oxlint 或 Biome。项目在 TypeScript 7.0.2 上，typescript-eslint 装不上。
2. **两处止血（第 3 周）。**
   - **等回答时，翻页、选字、点工具栏、切窗口都不再取消请求。**
     - 现状：请求本来就由主进程持有，`SurfingRequests` 按 requestId 管理；取消是界面主动发的。`main.tsx` 里的 Cruise 接管逻辑、`SurfingPanel.tsx` 的暂停和 `visibilitychange` 监听，都会调用 `cancelSurfing`。
     - 要改的：这些阅读动作不再调用它；面板按 requestId 重新接上结果；回答到了，用轻提示告诉读者。
     - 同步修改 `tests/cruise-takeover.test.ts`，并删掉验收脚本里失焦取消的特殊处理。
     - 改完以后，只有"停止"、新问题、关闭文档才会取消。
     - 请求在后台继续以后，开着 Surfing 用现有的 profile 开关测一次滚动和翻页，最长的一次任务不超过 50 ms。
     - 有余力的话，顺便把面板的请求状态拆成一个纯模块，配上单测。
   - **两个读者马上会碰到的小问题。** 三处发送范围说明统一成一处（P5，涉及对外承诺）；带路结束后归还空格和方向键（P10）。
3. **黑匣子（第 4 周）。**
   - 每次 Surfing 运行写一份 JSONL trace。事件包括：开始；每步请求（模型、参数、前缀哈希、token 估算）；每步响应（finish_reason、用量、缓存命中、思考 token、耗时）；工具调用；工具结果；校验违规；纠错；结束。
   - **默认只记这些**：事件类型、时间、模型和参数、token 数、passage id、页码、文档哈希、各部分的大小。问题原文、论文正文、页面图和回答正文默认都不记，API Key 任何时候都不记。
   - **调试模式**由你显式打开，打开后才保存原话，用于回放和诊断。
   - trace 默认只保留最近 200 次或 30 天。设置页提供"打开日志文件夹"和"清除"。
   - 读取厂商用量（M4）：请求带 `stream_options.include_usage`；流要一直读到 `[DONE]`，不在 `finish_reason` 处停。
   - 提示词从代码字符串搬到单独的文件，带版本哈希。
   - 从第 1 周推上去的 WIP 分支里，挑出运行记录（`surfing-run-log.ts`）的有用部分，在 main 上照着重写。不整段合并，因为它基于旧基线，纠错回合已经重复。
   - 有余力的话，让 agent 写一个简单的 HTML trace 查看器，之后每周读 trace 会轻松很多。
4. **不开窗口的评测 runner（第 5 周）。**
   - `npm run eval` 直接构造 `SurfingRuntime(ports)`。
   - 抽取结果按 PDF 的 sha256 加 parserVersion 缓存；页面图预先渲染好。
   - token 计数要么先构建 worker，要么在进程内直接计算。
   - `generate` 注入一个"录制 fetch"，支持录制、回放、直连三种模式。回放时按规范化后的 messages 匹配，忽略请求头和字段顺序。
   - 每条结果写一份清单：提交号加 dirty 标记、题集哈希、提示词哈希、parserVersion、请求的主机、请求的模型和响应里实际返回的模型、思考档、max tokens、温度、试次序号、用量、费用、延迟。
   - 失败先分成五类，分开统计：评测故障、基础设施、格式、过程违规、答错。
   - App 内测试模式和命令行共用同一个评测核心。
5. **题集 v0 和抽取回归集（第 6 周）。** 写题是读论文的活，不是写代码。从第 2 周的周末起，周末的学习时间基本都用来写题，这本身也是在学怎么做评测。每周 1 篇论文，4 篇在第 5 周的周末写完；来不及的话，第 4 篇可以拖到第 6 周的周末。写题估计要 12 到 16 小时，不算进施工时间。
   - **规模**：4 篇论文、24 到 30 题，全部作开发集。留出集，以及扩到 v1（8 到 10 篇、60 到 80 题），放到第二季度。
   - **论文**：大部分是 2026 年 6 月以后发表、CC BY 许可的 arXiv 论文，其中 1 篇中文、1 篇双栏且带连字和公式。Attention 另加，只当"记忆对照组"，沿用现有的题，不占 4 篇和 24 到 30 题的名额，也不计入主分。扫描件和长文放进 v1，目前预期失败，先记录失败方式。
   - **题型**：事实查找约 30%；图表题约 25%，每道配一题"同页但不需要看图"的对照；跨页综合约 15%；论文里没有答案约 15%；批判性阅读约 15%。另外加 5 条"带我读这篇"的无问题用例，记录生成切入点要多久。
   - **金标**：每题写原子化的关键事实。证据写成"页码加 1 到 3 段原文引文"，不用会随抽取变化的 passage id。
   - **闭卷探针**：每题先不给论文跑 3 次，2 次以上答对的剔除或标记。
   - **抽取回归集 v0**：
     - 用同一批论文，分两步人工标注。第 6 周先标章节标题和图表标题全文，第 11 周修图表索引要用。段落顺序在第 9 周之前补上，做法是在现有抽取结果上改，不从零开始标；这也是周末的活。
     - 写一个 `npm run eval:extract`，不调用任何模型，输出三个数：段落顺序正确率、章节标题召回率、图表标题召回率，都带 parserVersion 和提交号。
     - 以后凡是改抽取，先过这一关：三个数都不低于改动前。这一关不花钱，过了再做真实模型测量。这样抽取错误就不会被算到 agent 头上。
6. **分层评分器（第 6 周）。**
   - **第一层，代码检查**，免费且确定。检查答案：JSON 合法、id 存在、证据命中、数字题的数字原样出现在引文里、必看图的题看了对应页。检查带路的每一步：id 存在、按阅读顺序排、步骤里提到图 N 时那一页确实看过。这一层是门槛，单独报告，不算进主分。
   - **第二层，二元 LLM 评委**，每个维度只判一件事：答案包含哪条关键事实；每句话是否被引文支持；带路的每一步是否被这一步的段落支持。
   - **第三层**，你自己每周读 20 条 trace，做开放式标注。
7. **统计方法和决策规则（第 6 周，`docs/EVAL.md`）。** 下面的计算都由 eval 脚本自动输出，不用手算。
   - **主分**：可回答的题里，关键事实全部答对的比例。另有四个子分单列：图表题、"论文里没有答案"、带路、引用支持率。
   - **误差范围**：每个分数旁边写一个误差范围（Wilson 区间，可以照抄 bayes_evals 的做法），同一篇论文的题算作一组。题少的时候，只有差得很多才看得出来。估算一下：30 题时两个版本大约要差 15 到 20 个百分点，80 题时约 12 个百分点。
   - **比较两个版本**：看同一道题在两个版本上的得分差，再算这些差的平均值和误差范围。误差范围两头都大于 0，才能对外说"变好了"。
   - **A 类改动**：重构、界面、对模型回复的解析和校验，也就是不改变发给模型的内容的改动。回放必须 100% 通过，不跑真实模型。凡是改了抽取或提示、让发给模型的内容变了的，都算 B 类。
   - **B 类改动**：提示词、协议、引用单位、抽取。开发集每题跑 3 次。同时满足下面几条才合并：
     - 主分和引用支持率的点估计下降不超过 5 个百分点；
     - 图表题、"论文里没有"两类，各自下降不超过 2 题；
     - 纠错率和费用上升不超过 20%；
     - 读过至少 10 条有变化的 trace。

     这里的"一题答对"指 3 次里至少 2 次答对。没过时，先在同一提交上再跑 3 次，合并 6 次的结果再判断一次（6 次里至少 4 次答对算这题答对），因为什么都没改的版本也可能单凭随机波动被拒。

     这是粗筛，不是"没变差"的证明。题少时，它只能拦住明显的退步。
   - **C 类**：宣称支持新厂商。20 题冒烟各跑 1 次，不纠错就输出合法 JSON 的比例不低于 95%，否则在设置里标"实验性"。冒烟结果只用来标"已验证"或"实验性"，不当作质量结论。
   - **评委能不能用**：和你人工标的 50 条相比，评委判"支持"和判"不支持"的准确率（TPR、TNR）都不低于 0.8。达不到的维度，先只用代码检查加人工。
8. **第一次可信的基线（第 7 周）。** 这是之后所有决定的起点。
   - 在 main 上用 deepseek-flash 跑开发集，思考开、关各每题 3 次。
   - 用 DeepSeek 实际返回的 prompt_tokens 重测 Attention 的提示大小，作为 token 的正式基线。
   - 从基线回答里抽 50 条，人工标引用支持，用来校准评委。
   - 读 50 条 trace，做出失败分类表。

**完成标准**：失败里评测自己造成的低于 10%；每次运行都有清单；改一次提示词，能在半小时内、花不到 1 美元（关思考这一档）拿到一个带误差范围的对比结果。

**花费**：第 1 阶段的真实模型调用合计约 5 到 15 美元（估算），主要花在第 7 周的基线上。周五"单模型 1 美元"的上限只管关思考这一档。里程碑实验（第 7 周的基线、第 12 周的 A/B）和需要开思考的 B 类测量单列预算，不受这个上限约束。

### 第 2 阶段：让 harness 可靠（第 8 到 12 周，后半部分在第二季度）

**目标**：Surfing 的可靠性由应用决定，不取决于模型听不听话、开没开思考。每一步都用第 1 阶段的仪器测，过了决策规则才合并。

1. **循环分层（第 8 周，A 类，只用回放，不花钱）。** 先拆，再加新策略。现在的 `execute()` 是全仓最难读的代码，直接往里面塞预取和校验门，你自己没法审 diff。
   - 把 `SurfingRequests.execute()` 拆成 reducer、策略和机制三部分。错误换成有类型的错误，但外部行为保持不变。现有的 3 个工具搬进工具注册表。
   - 录一批真实的 DeepSeek 流当测试夹具，覆盖 8 类：
     - 正常回答；
     - JSON 动作；
     - 坏 JSON；
     - 带 reasoning_content 的思考；
     - 用量在最后一块；
     - OpenAI 风格、`[DONE]` 前 choices 为空的用量块；
     - 400 错误；
     - 中途断流。
   - 拆完以后，再补上几处脆弱点。它们都不改变发给模型的内容，仍算 A 类，但会改变某几个夹具的结果，所以每处配一个新夹具，写明预期的新结果：
     - 429、5xx、断流、空回复，各自动重试 1 次，计入预算。重试时界面显示"连接中断，正在重试一次"，trace 里也记一笔；
     - 整题的 token、时间、请求数上限放进策略层，并写进 trace；
     - 一条回复里有多个 JSON 对象时，取第一个合法的；
     - 去掉静默降级：出错时明确报出是哪一类错误，不再悄悄换一种方式继续（E10）。
   - "工具出错时把错误回传给模型"会改变发给模型的内容，属于 B 类，放到第二季度和原生工具调用一起做。
   - 完成标准：先做纯拆分，原有夹具的结果在拆分前后逐项相同；再加上面三处，新夹具按预期通过。
2. **固定提示顺序，改掉提示里矛盾的 scope 说法（第 9 周，小的 B 类）。**
   - 提示按固定顺序组装：系统提示、工具说明、论文段落，最后才是问题。同一文档、同一解析器版本时，前面这些逐字节相同，DeepSeek 的磁盘缓存就能命中。
   - 顺带改掉提示里 `scope:'extracted-text-only'` 和"能看图"之间的矛盾（H12 的前一半）。
   - 这两处都只改提示文字，作为一个组件一起测，第 9 周的周五测一次。除了正确率，也看缓存命中率和费用。
3. **引用单位从"行"改成段落（第 9 周开工，第 10 周测量，B 类）。**
   - 段落合并和双栏排序的算法参考 Cruise（`src/renderer/cruise-blocks.ts`），但要移植到 Python 的 `surfing_document`。Cruise 处理的是 PDF.js 的文本，Surfing 用的是 PyMuPDF，不能直接拿来用。
   - 每段保留逐行 quads 和字符区间。
   - id 改成短编号，例如 `P12`，句子写成 `P12.3`，并带上 parserVersion。现在 passage id 里的页码从 0 起（H12 的后一半），换成新编号后一并解决。
   - 注意：短编号仍然按位置排，抽取一改就会漂移，只能在一次回答之内用，不能当证据的长期身份。长期身份用第二季度的稳定锚点。
   - 第 9 周放在默认关闭的开关后面开发，第 10 周打开测量。先过抽取回归集，三个数都不低于改动前，再做 B 类测量。目标：提示 token 比基线少一半以上；打满 8 条引用上限的比例明显下降；正确率按决策规则不降。
4. **修图表索引（第 11 周，离线，不花钱）。**
   - 现在的正则要求编号后面紧跟冒号、句点或竖线。"Fig 3 shows""图1 模型结构""Figure S1""表 2-1"这类标题都会漏掉，"图 3.2"还会被当成图 3。
   - 要做的：放宽正则；把跨行的标题合成一整段；把正文里"Fig. N""图 N"这样的提及链接到对应的图。
   - 完成标准：抽取回归集上图表标题的召回率不低于 95%，含中文论文。
5. **图表题预取加代码校验门（第 12 周）。**
   - **什么时候预取**：问题里出现 Figure、Fig.、Table、图、表加编号时，按图表索引找到所在页，第一轮请求就附上这页的图，最多 2 张，作为 user 消息的附图。没有编号但像图表题（"这张图""这条曲线"）时，用图表索引的关键词匹配；匹配不上，就仍由模型自己决定。
   - **模型不支持看图时**（按现有代码里的视觉能力判断；能力档案要到第二季度才做）：跳过预取和下面前两道检查，回答直接标"此模型看不到图"。
   - **回答被接受前的三道检查**：
     - 判定为图表题的，目标页的图确实进过上下文；
     - 回答或带路步骤里提到图 N，那一页确实看过；
     - passageIds 都存在。
   - **前两道没过时**：由代码自动附图重跑一次。这次重跑计入整题预算，界面上显示"正在补看第 x 页的图"，trace 里也记一笔。仍然失败就照常显示，但标注"未查看图像"。
   - 引用超过上限时，由代码截断，不再为此进纠错回合。
   - **用一个小 A/B 验证**：A 臂让模型自己决定，B 臂由应用预取。固定 deepseek-flash，思考开、关两档，每题每臂至少 3 次，预算约 10 美元。
     - 题集里要有不点名图号的图表题，否则预取会直接满分，证明不了什么（review 的 V11）。
     - 95% 这个目标只在图表索引找到了的题上统计，漏检的题单独列出。

第二季度继续：

6. **小 bug 批次（2 月，寒假里，适合低强度）。** 现在只有 DeepSeek 验证过，也还没有外部用户，这几个 bug 可以等到这时。每个配一条回归测试：
   - OpenAI 推理模型改发 `max_completion_tokens`，并且不发 `temperature`（M2）；
   - 同一个标识不能连续撤销（W7）；
   - 移动过的便签，导出后回到原位（W3 的前一半，会丢用户数据）；
   - 星火的输出上限（M8，前提是第 2 周决定保留星火）；
   - 实机核实两个疑似问题（P15）："Markdown 原样显示"和"清空对话后可能仍发出旧对话"，确认了就修。
7. **文本清理（B 类）。** 修连字和断词，同时保留"规范化文本到原始字符"的偏移映射；去掉跨页重复的页眉页脚；每段带章节路径，提示开头放一份带页码的大纲。先过抽取回归集，再测。
8. **注入卫生（B 类，单独测）。**
   - 抽取时标记隐藏文字，也就是透明、白色、极小字号或超出页面的文字。送给模型前剔除，并在界面上提示"本页有隐藏文字"。
   - 题集里加 1 份藏着白字指令的测试 PDF。
   - 回答坚持纯文本渲染；Surfing 里不加任何联网工具。
9. **模型端口和能力档案。**
   - 在 `ai-client` 前面加 ModelPort，先只用 AI SDK 的 `@ai-sdk/deepseek` 实现，旧客户端留一个开关作回退。
   - 能力档案有三层：打包的快照；设置页里的"验证这个模型（约几分钱）"按钮，用户点了才发请求；手动覆盖。设置页显示"已验证"或"实验性"。冒烟测试覆盖流式、多轮、看图、JSON 和用量读取。
   - 守住现有的网络边界：provider 通过 `fetch` 参数接现有的受限 fetch，只走 HTTPS、拒绝重定向，参数仍然过白名单。写一条单测，断言请求只发往用户填的地址。
   - AI SDK 的几个坑：
     - 始终传 provider 实例，不传纯字符串模型名，否则请求默认会经过 Vercel 的网关；
     - `@ai-sdk/openai-compatible` 的 `includeUsage` 默认关闭，要显式打开；
     - 发行版不注册 telemetry，注册后它默认记录输入和输出；
     - DevTools 只在开发时用，它会把内容明文写进 `.devtools/generations.json`。
   - 完成标准：在同一批录制流上，新旧客户端产出的事件序列和最终答案逐项相同。回放在 ModelPort 事件这一层做，避免请求头变化导致对不上。
10. **原生工具调用，从 DeepSeek 开始（放在开关后面）。**
    - 工具参数用 `strict`，这需要 beta 地址。
    - 思考模式下，历史里所有轮次的 `reasoning_content` 都要回传，空的也要发，否则第二步就会 400。
    - 最终答案也做成一个 `answer` 工具，参数是 text 和 citations。
    - 工具出错时，把错误作为工具结果回传给模型，不再终止整题（H7）。JSON-in-prompt 路径也照此修改。这会改变发给模型的内容，按 B 类测。
    - 不支持原生工具的厂商继续走 JSON-in-prompt，这条后备路径一直保留。
    - 绝不在思考模式下发 `required` 或指定函数。

**完成标准**：
- 图表题在两档下都看了目标页的比例不低于 95%；
- 回答期间的阅读动作不取消请求；
- 提示 token 减半；
- trace 能回答每一次"它为什么这样做"。

### 第 3 阶段：证明对读者有用（第 6 周起，到 2027 年 5 月）

**目标**：用真实读者的数据定下 Surfing 的主路径，不再只由开发者一个人的体验决定。

1. **第一次让真实读者用（第 6 周，不需要新代码）。**
   - 请 1 到 2 位同学用现有版本读一篇论文，你在旁边只看不教。
   - 重点看两件事：他们会不会主动提问；给他们"带我读这篇"的入口时（先用一句固定的问题代替），他们怎么用。
   - VISION 说"Surfing 的定位"是冻结后第一个要做的产品决定。这里分两步走：这一轮先观察，第二季度的测试里再确认。
2. **改默认入口（2 月，排在前 12 周剩下的技术活前面）。**
   - 去掉"结论先行，再自动带路"，改为读者发起、读者控速。答案出现前先显示原文段落；带路默认不自动播放；"直接告诉我答案"保留为一个明确的按钮。这也是产品计划 v0.5.1 §3.3 说的"速度和深度必须独立"。
   - 加两个"让读者先动脑"的小设计：开始前"先猜一句"，结束后"用一句话复述"。两个都可以跳过。
   - 保留一个"带我读这篇"的按钮作为候选入口，留不留由下一条的测试决定。
   - 把"AI 什么时候说话"的规则写进文档：只在被请求时说；在原文旁边说；先给原文，再给解释；不主动打断。
   - 余额不足、参数错误、限流、网络四类错误，改成中文提示（M5），同学测试时一定会碰到。
3. **5 位同学的出声思考可用性测试（第二季度，开学后，约 3 月）。**
   - 用同一篇论文，有、无 Surfing 各读一段，配理解小测。记下他们卡在哪里，整理出前 3 个问题。
   - 测试脚本加上产品计划 v0.5.1 §7 的两个问题：多久得到第一个有用的理解；读第二篇时是否自愿再用。
   - 固定加一项任务：不提问，直接用"带我读这篇"读一段。判断标准建议写成：5 人里至少 3 人主动用它，并且读完能说出论文的主线，就保留这个入口。这是"Surfing 定位"这个决定的第二步。
   - 这一轮不求统计结论，求的是看清真实读者怎么用。
   - 实验前由你替他们配好模型，这一点要记下来，因为它会让结果偏向"有人带着用"。
4. **研究模式构建。**
   - 研究模式只放在单独的研究构建里，锁定提交、模型、思考档和提示词。
   - 每篇论文预先生成"直接给答案"和"一步步带读"两种条件的输出，人工逐条核对后冻结，实验时不现场调用模型。
   - 本地记录过程数据（停留时间、引用点击、带路完成度），用匿名编号，可以导出 CSV。
   - 知情同意书写明数据保存多久、什么时候删除。
5. **12 到 18 人的小研究（2027 年 4 到 5 月，避开春节和期末）。**
   - **设计**：每位同学三种方式都用一遍，这叫被试内设计。三种方式是：不用 AI、直接给答案、一步步带读。同一篇论文不能读三遍，所以要 3 篇论文，每篇 8 到 12 页、难度相近、各有一张关键图、不是名作。顺序用一张轮换表（3×3 拉丁方）安排，让每种方式排在第一、第二、第三的次数一样多。
   - **题目**：每篇 3 道字面题、3 道推理题、2 道图表题、1 道迁移题，其中至少一半不在 AI 答案的覆盖范围内。读完做 3 分钟复述；每题打 0 到 100 的信心分；3 到 7 天后做一次延迟小测。
   - **主指标**：推理、迁移加复述，开跑前写死。复述由不知道条件的同学打分，也就是盲评。
   - **信心校准**：看读者打的信心分和实际对错是否一致。比如信心 90 分的题，真能答对九成左右，就是校准得好；信心很高却常常答错，就是"觉得懂了，其实没懂"。具体算法在研究方案里写死。
   - **程序**：开跑前把要看的指标公开写下来（预注册，用 AsPredicted 或 OSF），免得事后挑好看的报；找学校的伦理委员会、科研办或一位老师挂名指导；准备知情同意书。
6. **按结果定方向。**
   - 一步步带读不比直接给答案差，而且信心校准更好：把"读者主动带路"做成主路径，"安静伴读"作为默认层。
   - 直接给答案更好：保留问题优先的 Surfing，加上"先猜一句"和"一句复述"，并告诉读者它只覆盖你问的那个问题。
   - 不用 AI 最好，或者用 AI 时信心校准明显变差：收缩成安静伴读，带路只作为选项。
   - 不论哪种结果，都把"复述加原文引用"存成证据卡。作者是读者，AI 只提议。这一步接上第 5 阶段。

**进入下一阶段的条件**：有一份带数据的方向结论，并写进 VISION。

### 第 5 阶段：证据，以及 AI 安全地写入（预计 2027 年暑假以后）

对应 VISION 的第二阶段。

**进入条件**沿用 VISION：阅读实验有了初步结果；有人在演示之外真的反复使用；Reader 的性能达到预算。另外加两条技术前提：引用支持率有了基线；稳定锚点已经完成。

下面第 1 条本身是在修 bug（W1、W3），第二季度就做，不等这些条件。

1. **先修写入政策和导出溯源，再开放任何 AI 写入（第二季度）。**
   - AI 身份只能产生"建议"状态的标识：不能自己采纳，不能改或删用户的标识。采纳只能来自读者真实的点击。
   - 来源拆成两个维度：谁提议的、谁采纳的。在 EDITING.md 里统一"临时"这个词，写明"建议 = 来源是 AI、尚未采纳"（W2）。
   - 导出默认排除未采纳的建议。已采纳的 AI 来源标识在 PDF 里标明，不再一律写成 `author:'user'`。
   - **稳定锚点（同在第二季度，必须在写入之前完成）**：每条证据存文档指纹、parserVersion、引文和前后约 32 个字，改了抽取也能找回原位置，配一条回归测试。同时测一次"Surfing 段落转成编辑库文字锚点"的成功率，这件事从没测过（W4）。
2. **写入 v0：带路里的"留下这段"按钮。**
   - 模型只负责选段，用的是已经校验过的 passageIds，不新增输出格式。
   - 读者点了按钮，才以读者身份写入高亮。来源存稳定锚点，不存 `P12` 这样的短编号，同时记下是哪一问、哪段回答、哪个模型、什么时间。
   - 写入后弹出一个可跳过的一行输入框"我的理解"。这就是第一张证据卡。
3. **写入 v1：建议托盘。**
   - 回答里可以带 0 到 3 条提议。每条包含 passageId、类型（证据、定义、方法、局限、问题）和不超过 120 字的说明。
   - 坐标由宿主解析，模型永远不给。
   - 建议在页面上用虚线样式显示，可以逐条采纳或忽略，没有自动采纳。
   - 确认只放在"采纳"和"导出"这两个有后果的点上，不要每条都弹框，否则读者会习惯性地全部点"是"。
4. **证据卡和检索。**
   - 一张证据卡包括原文位置（文档指纹、页码、锚点）、引文和读者自己的理解；读者的理解和 AI 的解释分开存放。
   - 问答记录可以存下来，作为证据卡的来源之一。现在关掉窗口就没了（P13）。
   - 可以在自己的所有证据里跨文档检索。
   - 导出带出处的引文：先支持 APA，再支持 BibTeX。
   - 提供 `enlumor://` 链接，点开就回到原文。
   - 和 Zotero 互通，先做读条目和引用键。
5. **在页面上直接拖动便签、线条端点和画笔。** 这是 ROADMAP 里已有的编辑体验需求。
6. **编辑库瘦身。**
   - 修好 `--legacy-editing` 在 v5 工作区上导出过期批注的问题，或者直接禁止 legacy 导出（E8、W8），并定一个移除日期。
   - 对照现在的产品承诺，删掉为"通用 AI 编辑者"准备、但用不上的机制。

### 第 6 阶段：把 Enlumor 开放给用户自己的 agent（MCP，第 5 阶段之后）

按 VISION，MCP 放在证据阶段之后。要不要提前，见第十节。

**前提**：
- 段落单位和稳定锚点已经完成。否则行级 id 和 2 万 token 的全文转储会变成对外契约，而且 Claude Code 默认会截断超过约 2.5 万 token 的工具输出。
- 建议托盘已经能用，因为 MCP 的写入也要进同一个托盘。

1. **先写一页架构说明。** MCP 服务器是外部 agent 另起的一个本机小程序，要先想清楚它怎么拿到文档和抽取结果：是连到正在运行的 Enlumor，还是自己读工作区数据库、自己调用 Python 抽取。这一点不先想清楚，原型会做歪。
2. **v0：只读的 stdio 服务器。**
   - 大约 6 个工具，都加 `enlumor_` 前缀，标上只读提示（`readOnlyHint`），带输出 schema，默认分页：列出文档、文档大纲、搜索、按 id 读段落、取页面图、读证据卡。
   - 读证据卡时默认只给引文和位置，不给"我的理解"。
   - 读取也要授权：外部 agent 第一次连接时，由 Enlumor 弹窗。读者可以限定"只开放当前打开的文档"或"只开放我勾选的文档"。
   - MCP 发出去的内容，写进 4.3 节那份唯一的说明。
3. **v1：只开放一个写工具 `enlumor_propose_annotation`。**
   - 结果进第 5 阶段的同一个建议托盘，并标明来自哪个客户端。客户端自报的身份要标"未验证"。
   - 某个客户端第一次提交时，由 Enlumor 自己弹出授权。写入的拦截必须放在 Enlumor 这一侧，不能依赖客户端的审批，因为用户可以把客户端的审批全关掉。
4. **不做：**
   - 监听 0.0.0.0：会让局域网里的其他人也能连进来；
   - MCP sampling：外部 agent 反过来借用你配置的模型；
   - A2A、AG-UI、MCP Apps：这几种是 agent 之间互相通信、或在外部 agent 里嵌入界面的协议，现在都不需要。

### 第 7 阶段：长文、扫描件和结构（按真实需求触发）

**触发条件**：有真实用户带来长文或扫描件，或者题集里这两类失败成了主要问题。

- **长文模式**：
  - 文档估算 token 超过模型窗口的一半时，不再发全文，改发大纲、摘要、引言、结论原文和图表清单。
  - 再提供段落级的 BM25 搜索（一种经典的关键词检索算法）和 `read_section`。到这时，`search` 和读取类工具才真正派上用场。
  - 原来超过 16 万字符或 1 MiB 就直接失败，改成自动切换到这个模式。
- **扫描件**：
  - 第一步只做检测，明确告诉读者"第 x 页是图像，AI 看不到文字"，这些页只能看图。
  - 第二步再接可选的 OCR：用 PyMuPDF 的 OCR 插件加 RapidOCR，作为可选下载，不默认打包。OCR 出来的文字标明来源。
- **PyMuPDF 2.1 的内置 layout**：
  - 先在单独的分支上核实许可证，看模型权重是否兼容 AGPL，再测打包体积和速度。
  - 然后在抽取回归集上和第 2 阶段的启发式做对比，再决定升不升级。
  - 不要在 1.28.2 上装 `pymupdf-layout` 1.x：它是非商业许可，不能和 AGPL 一起分发。
- 不用 VLM（能看图的大模型）生成的文字替换原生文本层去做引用和高亮。生成的文字可能和原文不一致，违背"原文优先"。

### 第 8 阶段：论证与写作（VISION 第三阶段）

**进入条件**：用户确实在多篇论文里积累了证据，并且有人主动想在写作时用它们。

- 论证提纲：每个论点（Claim）下挂着支持它的证据（Grounds）、为什么能支持（Warrant），以及反方观点（Counterargument），每条证据都能点回原文。
- AI 的角色是检查：哪个论点缺证据，哪条证据其实不支持论点，哪里的推理有跳跃。它不生成整篇文章，也不编造引用。
- 先导出 Word 和 Markdown 能用的提纲和引文，LaTeX 和 BibTeX 作为研究生选项。

## 七、工作节奏和硬规则

### 每周

- **周一 1 小时，计划。**
  - 读 STATUS.md 和上周五的评测记录，选本周唯一的主题。
  - 最多拆成 3 个 PR 大小的任务，几个小 bug 可以合成一个任务。
  - 每个任务写一句"做到这样算完成"，最好是一条能跑的命令或检查。
- **周二到周四，每天约 2 小时，施工。**
  - 每天一个主会话，在一个 worktree 里只做一个任务。
  - 最多同时开 2 个会话，而且改的区域不能重叠。比如一个改 `src/main`，另一个只写测试或文档。
  - 一个任务最好当天合并。做不完的大改动放在默认关闭的开关后面，分段合并。
  - 合并前开一个新会话，对照"完成的定义"做 review；你自己读 diff 的摘要，并亲手跑一次应用。
  - 同一件事纠正两次还不对，就清空会话、重写提示。
- **周五约 2 小时，测量。**
  - 第 1 到 6 周还没有可测的东西，周五也用来施工。
  - 从第 7 周起：用固定题集，每题跑 3 次，记录提交号和配置，设好预算上限（单模型不到 1 美元）；读 20 条 trace 做标注；更新 STATUS.md。
- **周末 3 到 4 小时学习，30 分钟对外交流。**
  - 对外交流可以是发一个具体问题，或约一位同学来试用。
  - 第 2 到 5 周，周末的学习时间基本都用来读论文、写题，6.1 表里这 4 周的"同步学习"改为可选，没时间就挪到第 7 周以后。第 6 到 8 周的周末，补抽取回归集的标注。

### 硬规则

- 未合并的 PR 不超过 2 个；一个分支最长存在 3 个施工日。
- 不再搞代码冻结和 Wave 批次。
- 真实模型运行集中在周五；同一时间只跑一个 Electron。
- 写进文档的质量结论，必须引用同一提交上至少 3 次的运行。冒烟结果只用来标"已验证"或"实验性"。
- 通宵任务只交给能自动判对错的工作，比如修测试、格式化、补回放夹具；不交给新功能和产品决定。
- 每完成一个 harness 改动，你用自己的话写 3 句"这次 agent 循环改了什么、为什么"。写不出来就先不合并。这是在偿还理解债，也是最实在的学习方式。
- 某周的估计小时超出了就顺延，不压缩质量；期末周的量减半。

## 八、找人帮忙

学校里暂时没有研究 agent 的老师，但你需要的人不一定要懂 agent。你需要的是懂"怎么验证一件事做成了"的人，以及真实的读者。

- **同学读者**：他们是你现在最重要的评审。第 6 周先请 1 到 2 位，第二季度请 5 位。
- **一位老师**：不一定要懂 agent，最好懂统计、教育测量或研究方法。请他看一次评测方法和阅读研究的设计，并为研究挂名。
- **开源和社区**：
  - 在仓库开 GitHub Discussions，建一个"Design questions"分类。
  - 写一页英文的《Enlumor: 3 open design questions》，附 60 秒演示视频。问题比如：引用单位用段落还是句子；引用支持度怎么评；阅读时请求要不要能打断。发给 Semantic Reader 项目的作者，每人只问 2 到 3 个 10 分钟能答完的问题。
  - PDF 抽取问题（连字、上标、求和号、表格、双栏顺序）带上最小复现 PDF，发到 MuPDF 论坛。Zotero 互通的问题去 zotero-dev。
  - 在 Datawhale hello-agents 的讨论区、掘金或知乎写一篇《我怎样给 PDF 阅读 agent 做评测》，换回社区反馈。
- **项目制学习的机会**：关注 2027 年开源之夏和 GSoC 的公告，以学生身份去和 PDF、文献、AI 工具相关的社区做贡献，借此获得正式导师。哪些组织会参加，还没有核实。

目标：每月至少一次对外动作，3 个月内至少有 2 位外部人士给出实质反馈。

## 十一、现在明确不做的事

- 不跑约 330 美元的全因子评测矩阵，先做抽样矩阵。

- 不让 AI 不经读者确认就写入，不自动采纳，AI 不改也不删用户的标识。

- 稳定锚点完成之前，不发布 MCP，也不让 AI 写入。
- 不用 VLM 生成的文字替换原生文本层。
- 不在用户没点按钮的时候发验证请求，花用户的钱。
- 不做找新文献的检索和系统综述（Elicit、Consensus、SciSpace 的领域）；不做播客、闪卡、报告生成（Gemini Notebook 的领域）；也不在"方便地给答案"上和豆包、Kimi、ChatPDF 比。对外的一句话定位是：让你真的读懂一篇论文，并留下带原文出处的、自己的理解。

- **第二季度的任务做完时（预计 7 到 8 月）**：对照第三节最后一列逐项打勾，再检查第 5 阶段的进入条件是否满足。

每个检查点都把 VISION 里那几个问题再问一遍：

- 读者能不能更容易地开始读一篇陌生论文？
- AI 是在帮人形成自己的判断，还是让人只看 AI 的输出？
- 加了新功能以后，阅读和批注是否依然流畅？
- 有没有人在演示之外反复使用？
